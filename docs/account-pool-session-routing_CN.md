# 账号池与会话绑定路由方案

**状态：** 方案草案  
**适用场景：** 200 个用户、4 个正常账号、4 个风控账号，需要按模型能力分池，并限制账号并发数和活跃 session 数。

## 1. 目标

1. 风控账号只承担低能力模型流量，避免高能力请求被上游降级。
2. 正常账号承担所有可能在同一会话中切换到高能力模型的流量。
3. 一个会话在有效期内固定使用同一账号；模型切换不触发账号切换。
4. 账号并发不超过每账号 5 个请求，活跃 session 不超过每账号 10 个。
5. 绑定账号失效时，保留会话绑定；距上次有效活动满 2 小时后，下一次请求才允许重新绑定。

## 2. 已知条件与边界

| 项目 | 当前条件 |
|---|---|
| 用户规模 | 200 人：重度 20 人、中度 40 人、轻度 140 人 |
| 正常账号 | 4 个，可正常使用高能力模型，也可处理低能力模型 |
| 风控账号 | 4 个，响应较慢、算力有限；高能力请求可能被降级到低能力模型 |
| 日常需求 | 低能力模型可以满足大部分日常开放需求 |
| 账号请求并发 | 尽量不超过 5，5 为硬上限 |
| 账号活跃 session | 每账号最多 10 个 |
| 会话换号规则 | 活跃会话不可换账号；空闲满 2 小时后允许下一次请求重新选账号 |

用户数不等于同时活跃 session 数，也不等于同时执行请求数。容量判断需要结合实际请求率、上游响应时长、模型使用比例和 session 活跃窗口。

## 3. 术语与计数口径

- **逻辑 session**：客户端认为是同一段对话的稳定标识。绑定键应包含租户或 API Key 范围、provider 和稳定的 session ID，避免不同用户使用相同 ID 时发生冲突。
- **账号绑定**：逻辑 session 当前固定使用的凭据。绑定键不包含模型名。
- **升级型 session**：可能在会话过程中从低能力模型切换到高能力模型，因此必须从开始就分配到正常账号。
- **低能力专用 session**：明确不会在同一会话中请求高能力模型，可以分配到风控账号。
- **同时请求数**：当前正在账号上执行的请求数；请求完成、流结束或连接断开后释放。
- **活跃 session 数**：最近 2 小时内有有效上游活动，或仍有执行中请求/开放上游会话的不同逻辑 session 数。同一 session 连续请求只计一个 session。
- **绑定空闲有效期**：从最近一次有效上游活动开始计算 2 小时。达到 `last_active + 2h` 后，旧绑定过期；在此之前不得换号。

如果请求没有稳定 session ID，系统无法可靠保证会话粘性。需要从协议中提取可靠标识，或由网关向客户端提供稳定的会话标识。

## 4. 账号池与模型能力

### 4.1 账号分组

| 账号组 | 账号数 | 允许模型 | 主要用途 |
|---|---:|---|---|
| `normal` | 4 | 低能力和高能力模型 | 升级型 session；高能力请求 |
| `restricted` | 4 | 明确配置的低能力模型 | 低能力专用 session |

模型资格使用规范化后的模型 ID 和明确的账号能力配置判断，不以模型名称或临时错误猜测账号能力。高能力请求的候选集必须排除 `restricted` 账号。需要监测请求模型与上游实际服务模型；发现静默降级时，应记录为能力不匹配，不能将其报告成高能力调用成功。

### 4.2 会话类型

会话类型在首次请求前确定，并在会话有效期内保持不变：

- `upgrade-capable`：只从正常账号池选账号。即使首个请求使用低模型，之后切换到高模型也继续使用该正常账号。
- `low-only`：优先从风控账号池选账号。若业务允许，也可在创建新 session 时溢出到正常账号；一旦选定正常账号，后续仍固定使用它。

建议默认类型为 `upgrade-capable`，只有明确为低能力专用的 API Key、用户策略或会话策略才进入 `low-only`。仅根据首个请求的低模型名无法判断该用户之后是否会升级。

低能力专用 session 后续请求高能力模型时，不得切换到正常账号。应返回明确的会话能力错误，并要求客户端创建新的升级型 session。正常账号上的 session 可以在同一账号内自由切换低、高能力模型。

## 5. 绑定与重新绑定流程

### 5.1 首次请求

1. 提取租户/API Key 范围、provider 和稳定 session ID。
2. 确定 session 类型及所需模型能力。
3. 构造合格候选账号：账号状态可用、账号组匹配、模型在允许范围内，并且账号并发和活跃 session 均未达到上限。
4. 在合格候选中选择负载较低的账号。负载至少参考 `in_flight / max_in_flight` 和 `active_sessions / max_active_sessions`。
5. 原子地创建 session→账号绑定，并登记 session 名额及请求并发名额。并发创建同一个 session 时，所有请求必须收敛到同一个绑定。

### 5.2 已绑定 session

如果 `now < last_active + 2h`：

- 后续请求继续使用绑定账号，不因模型切换、优先级变化或其他账号更空闲而重新选号。
- 每个请求仍要经过账号并发准入；session 名额只计一次。
- 若请求模型超出绑定账号能力范围，返回明确错误，不尝试换号。
- 若账号并发已满，等待或返回可重试错误；不可把这个 session 派给另一个账号。
- 若账号失效，保留绑定并返回账号不可用错误。允许在账号恢复后继续使用原账号；不可提前绑定到备用账号。

### 5.3 2 小时过期后的重新绑定

当 `now >= last_active + 2h` 且旧请求/连接已结束，旧绑定过期。客户端下一次请求到达时，系统可以重新选择符合 session 类型和模型能力的新账号，并原子创建新的绑定 epoch。

重新绑定应创建新的上游 session 身份，不能把旧账号的上游 session ID 或不透明 continuation ID 直接传给新账号。若需要延续用户对话，网关必须持有可重放的对话历史；如果客户端只有旧账号生成的 opaque response ID，则应要求客户端重建会话上下文。

`last_active` 建议在请求已被准入并实际成功建立上游活动后刷新。纯本地限流、账号认证失败和失效账号上的重试不应刷新期限，否则用户持续重试会让失效绑定永不过期。流式请求或 WebSocket 在执行期间应保留绑定；未结束的请求不能被过期清理任务换绑。

## 6. 并发、session 限额与公平性

### 6.1 账号级硬限制

- `max_in_flight`：每账号硬上限 5，所有模型共享该账号的额度。
- `max_active_sessions`：每账号硬上限 10，按不同逻辑 session 计数，而非请求数或模型数。
- 已有 session 的请求只使用绑定账号的名额；不能在超限时通过切换账号绕过上限。
- 新 session 在账号已满时可以尝试同组其他账号；该组均满时排队或返回带 `Retry-After` 的可重试限流响应。
- 账号失效时，该账号应从新 session 候选中移除；原 session 绑定记录保留到 2 小时过期。多实例部署时，绑定、配额和创建竞争必须由共享的原子存储或统一准入服务维护。

### 6.2 初始运行值

风险账号响应较慢，建议渐进开放，而不是首次就打满上限：

| 账号组 | 初始并发目标 | 硬上限 | 活跃 session 硬上限 |
|---|---:|---:|---:|
| 正常 | 4/账号 | 5/账号 | 10/账号 |
| 风控 | 3/账号 | 5/账号 | 10/账号 |

据此初始并发目标约为正常池 16、风控池 12，合计 28 个请求；理论硬上限为 40 个请求。根据上游延迟、限流和降级数据逐步调高风控账号并发，但不超过 5。

### 6.3 用户公平性

账号绑定按 session 而非静态按用户分配，避免把多个重度用户固定到同一账号。另需设置用户级活跃 session 上限或公平排队，防止单个用户创建大量 session 占满账号名额。重度、中度、轻度标签可作为排队权重或服务配额依据；若这些标签只是使用量描述，则不应自动变成优先级承诺。

正常账号承担升级型会话，低模型溢出到正常池会消耗高模型容量。若启用溢出，应单独限制正常账号上的低模型并发，并优先保留高模型请求额度。溢出只能用于创建新 session，不能迁移已有 session。

## 7. 容量推演

| 场景 | 容量结果 | 影响 |
|---|---|---|
| 正常账号：4 × 5 并发 | 最多 20 个同时请求 | 20 个重度用户若同时各发一个高模型请求，正常池已满；中度用户需要等待或限流。按初始目标 4/账号时只有 16 个请求名额。 |
| 正常账号：4 × 10 session | 最多 40 个升级型活跃 session | 20 个重度和 40 个中度用户若都需要升级型 session，需求 60，至少 20 个无法同时获得正常池 session。 |
| 风控账号：4 × 10 session | 最多 40 个低能力专用活跃 session | 140 个轻度用户不可能全部在同一 2 小时活动窗口内各占一个风控 session；多余新 session 需要等待、限流或经批准后使用正常池溢出额度。 |
| 全部账号：8 × 10 session | 最多 80 个活跃 session | 如果 200 人都在同一活动窗口内各有一个活跃 session，至少 120 个需等待或被限流。 |

这些数字是上限推演，不代表预计同时在线人数。应使用实际流量估算：并发需求约等于请求到达速率乘以上游平均响应时长；session 需求则按每账号在滚动 2 小时内的不同活跃 session 数统计。

## 8. 异常处理

| 情况 | 已绑定 session | 新 session |
|---|---|---|
| 账号并发满 | 留在原账号，等待或返回可重试错误 | 选择同组其他有容量账号；均满则排队/限流 |
| 账号临时冷却或失效，绑定未满 2 小时 | 不换号；返回原账号不可用及建议重试时间 | 排除不可用账号，选择同组可用账号 |
| 绑定已空闲满 2 小时 | 下一次请求允许重建绑定；新上游身份 | 按会话类型和模型重新选择 |
| 请求模型超出绑定账号能力 | 明确拒绝，不自动换账号或静默伪装成高能力结果 | 按所需能力选择兼容账号 |
| 缺少稳定 session ID | 无法保证跨请求粘性，应生成/要求稳定 ID 或按无状态请求处理 | 同左 |
| 绑定/准入共享存储不可用 | 不做无绑定回退；返回服务不可用，避免跨实例错绑 | 同左 |

## 9. 企业审计插件与核心职责

建议把职责分开：

- **企业审计插件**：维护账号组、模型能力映射、session 类型策略；为新 session 选择候选账号；记录选择原因和审计事件。
- **统一准入层**：原子维护 session 绑定、2 小时过期、账号并发数、活跃 session 数和账号失效状态。可以由核心/Home 准入层实现，也可以由插件背后的共享存储服务实现，但不能只靠插件对候选快照做本地计数。
- **执行器**：对绑定账号执行请求，并确保请求并发名额在请求/流/连接生命周期结束后释放。

当前仓库中，Scheduler 插件接口提供 provider、model 和候选账号信息，可让插件返回账号选择结果（[接口定义](../sdk/pluginapi/types.go#L490)）。该接口本身是选择决策，不是容量预留协议。内置 session 亲和键包含 model，且绑定账号不可用时存在重新选择路径（[亲和选择器](../sdk/cliproxy/auth/selector.go#L1039)），与本方案的“模型切换不换账号、失效后等待 2 小时”规则不一致。核心已有账号并发准入路径，但需确认所有目标 API 路由都经过统一准入（[路由准入位置](../internal/api/server_routes.go#L439)）。

当前代码仓库没有企业审计插件的实现源码，因此无法在本文中确认插件已经覆盖了哪些规则。落地前应按本方案第 10 节验收点审查插件和核心的实际组合。

## 10. 上线步骤与验收

### 上线步骤

1. 人工核对 8 个账号的能力和状态，配置账号组、规范模型列表及模型别名映射。
2. 确认各 API 协议的 session ID 提取方式；处理没有稳定 session ID 的客户端。
3. 影子记录账号组、请求模型、预测账号、并发、活跃 session 数、上游实际模型和错误，不改变现有路由。
4. 启用 session 级绑定和共享准入；正常账号初始并发目标设为 4，风控账号设为 3，所有账号硬上限 5、session 硬上限 10。
5. 观测高峰后按风控账号的 p95 延迟、错误率、降级率和池饱和时间调整并发及用户公平配额。

### 验收条件

- 同一 session 在 2 小时有效期内切换模型时，始终使用相同账号。
- session 绑定账号失效但未满 2 小时时，系统不静默切换账号；失败请求不会延长过期时间。
- 距最后一次有效活动满 2 小时后，下一请求最多创建一个新绑定，并使用新的上游 session 身份。
- 高能力请求不会选择风控账号；低能力专用 session 请求高模型时显式失败。
- 任意账号的同时请求数不超过配置值，活跃 session 不超过 10；多实例竞争时也成立。
- 账号失效、并发满、session 满、模型不兼容和绑定存储不可用都能返回可区分的结果及安全日志。
- 监控可以按账号组查看请求量、当前并发、2 小时活跃 session 数、等待/限流、失效绑定、重新绑定、模型降级和用户级配额命中。

## 11. 待确认策略

1. `upgrade-capable` 是否作为所有用户的默认 session 类型；建议默认是，以免首个低模型请求把后续升级锁进风控账号。
2. 正常账号是否允许承接低模型新 session 溢出；如允许，需确定每账号为高模型保留的并发额度。
3. 重度/中度/轻度是服务优先级，还是仅用于观察用户行为；若作为优先级，需要明确每类用户的并发和 session 配额。
4. WebSocket 等长连接是否在连接存续期间始终计为活跃 session；建议是，并且连接未关闭时禁止过期换绑。
5. 是否提供管理员提前结束失效账号绑定的紧急操作；该操作会绕过 2 小时规则，必须同时创建新的上游 session 身份并留下审计记录。
