04 · Enterprise access & audit

enterprise-access-audit

这是 CPA 的动态库插件，提供 Enterprise Key 模型访问限制、按策略记录用户文本请求，以及人工查看明确的上游 Cyber Policy 信号。插件默认不会自动封禁账号。

从 CPA-Manager（18317）管理插件：先在 CPA-Manager 的插件资源页面检查 Enterprise Access Audit 是否有效启用，再进入其策略和审计页面。动态库由 CPA 进程加载；仅复制文件或只更新前端不代表功能已启用，必须使用匹配版本和架构的插件、正确设置开关并重启 CPA。

1. 使用联合包内的匹配插件

支持插件的完整 Suite 归档包含对应系统/架构的插件，例如：

plugins/windows/amd64/enterprise-access-audit.dll
plugins/linux/amd64/enterprise-access-audit.so
plugins/darwin/arm64/enterprise-access-audit.dylib

使用与 CPA 相同 Release 的动态库；Windows、Linux、macOS 以及 amd64、arm64 不可互换。无插件兼容的归档（例如 *_no-plugin）不会加载该插件。

2. 启用插件

将以下配置合并进当前 config.yaml 的 plugins 块。若模板已含有 plugins:，只合并子项，不要再添加重复的 YAML 根键。

plugins:
  enabled: true
  dir: "plugins"
  configs:
    enterprise-access-audit:
      enabled: true
      priority: 100
      data_dir: ".cli-proxy-api/plugins/enterprise-access-audit"
      database_path: ".cli-proxy-api/plugins/enterprise-access-audit/enterprise-access-audit.sqlite"
      retention_days: 30
      audit_enabled: false
      default_audit_enabled: false
      max_text_bytes: 32768
  1. 确认动态库文件名为 enterprise-access-audit，并位于 CPA 插件目录的平台/架构子目录。
  2. 确认全局开关 plugins.enabled 与本插件开关 configs.enterprise-access-audit.enabled 都为 true。
  3. 使用 stop.bat / stop.sh 停止，再启动套件，使 CPA 重新加载动态库。
  4. 通过 CPA-Manager 的插件资源页面或管理接口确认 effective_enabled: true。接口为 GET /v0/management/plugins，需要 CPA 管理认证。

默认数据路径相对于 CPA 工作目录。保持目录权限受限；插件会在其中创建策略数据库与审计 JSONL 文件。

3. 管理页面主要功能

模型访问策略

给 Enterprise Key 配置禁止使用的模型 ID。命中策略时请求在发往上游前被拒绝；策略同时比较客户端模型名和解析/改写后的模型，避免别名绕过。策略身份按 Key Hash 关联。

请求审计

按日期、Key 等条件查询已保存的审计记录。只有明确开启审计的请求才新增记录；可设置全局开关、Key 单独开关和默认 Key 审计状态。

保留与文本长度

根据业务要求设置保留天数和单条用户文本上限。默认数据目录中 SQLite 保存策略/设置，JSONL 文件保存受限的审计记录。

人工查看安全信号

只在上游错误 JSON 的 error.code 或 response.error.code 精确等于 cyber_policy 时记录相应信号。

4. 审计默认关闭，按需开启

audit_enabled 是插件级全局请求审计开关，新配置建议保持 false。开启全局审计后，目标 Key 也必须允许审计才会写入；default_audit_enabled 仅决定没有显式 Key 设置时使用的默认值。

模型拒绝与审计是两套开关：全局审计关闭时不会新增请求审计记录，但已保存的模型禁止策略仍继续执行。要验证访问控制，应使用受控测试 Key 对允许/禁止模型分别发起请求。

审计只保留必要请求元数据和受限的用户文本。不会保存 system/developer 提示、assistant 对话历史、工具参数、工具输出或原始图片/音频/视频内容。API Key 不以明文保存，内部使用 Key Hash 关联策略与记录。

5. Cyber Policy 信号边界

只有上游响应结构明确返回下列字段之一时才标记：

{"error":{"code":"cyber_policy"}}
{"response":{"error":{"code":"cyber_policy"}}}

普通 HTTP 4xx/5xx、消息文本提及 cyber_policy 或 CPA 本地模型策略拒绝，都不构成该信号。记录用于人工复核；插件不会自动封禁用户、禁用账号或阻断后续会话。

6. 可选：Codex 账号池

账号池是同一插件中的可选调度能力，与审计无关，首次部署保持关闭即可。确需启用时，在插件的账号池资源页面按实际 OAuth 账号、用户绑定和并发策略配置，并确保没有另一个插件同时接管 Codex 调度。

  • 账号池只针对 Codex OAuth 账号；API-key provider 不纳入 OAuth 池隔离。
  • 用户绑定的活跃会话保持账号粘滞；不要期待失败或并发饱和时自动切换到另一 OAuth 账号。
  • 启用账号池前停用会竞争 Codex 调度/并发管理的其他插件，确认实际 scheduler takeover 状态。
  • 账号池的策略、部门绑定和并发细节请阅读插件完整说明 ↗，不要只照抄一个开关。

7. 故障排查

现象先检查
插件列表没有该插件全局开关、本插件开关、插件目录、文件名、系统/架构、CPA 日志和是否已重启。
页面没有 Enterprise Access Audit插件是否 effective_enabled: true；刷新 CPA-Manager，确认当前 Manager 与 CPA 版本配套。
审计没有记录全局审计开关和 Key 开关、请求是否在支持的文本协议范围、当前 Key 和数据保留设置。
模型拒绝规则不生效插件运行状态、策略所绑定的 Key Hash，以及客户端/解析后模型 ID。
动态库无法加载重新下载同一 Suite Release 的匹配归档，校验 SHA-256；确认没有误用 no-plugin 包。
完整字段、审计路径范围、数据格式和账号池行为见仓库内插件中文说明 ↗。通用安装入口见官方快速开始 ↗。
